# Beamer composition survey (excluding vertical-spacing core)

Scope: `packages/core/src/beamer/` (28.5k lines, ~100 files). All line numbers are for the working tree as surveyed. Read-only survey; no source edited.

## 1. Map

Churn: `render.ts` 39 commits. Of the 35 newest subjects, about 30 are list/alignment/block/column/display skip fixes ("Match Beamer list boundaries...", "Preserve Beamer column alignment scopes and display glue", "Keep a list's closing skip apart from an alignment box..."). `frame-flow.ts` 6 commits, all skip rules. Non-spacing files (overlay, footnotes, captions, shrink, theme) are almost untouched. So the structural problems below are in the flow/box machinery that spacing sits on, not in the leaf mechanisms.

## 2. Hotspots (ranked)

### H1. Three independent "vertical list of boxes" builders; no single box/vlist model
Locations: frame level `prepareFrameFlow` (render.ts:1570-1835); column level `prepareColumnFlowNode` + `prepareColumnContent` (3507-3684, 3685-3912); block body (2420-2540, which builds yet another flow loop, with an `onlyChild` / `children` branch and its own unsupported-placeholder handling); and inline (`prepareInlineFlow`, 1514-1568). Each re-derives previous-depth, first-in-container, leading baselineskip, `\lineskip` fallback and "starts in minipage" state, then calls the shared `positionPreparedFrameFlow` (frame-flow.ts:28), which itself assumes the leading skips have been pre-baked into the items.

Evidence of the same decision made in several places (the context flags show the missing abstraction):
- Column: `firstInColumn: flow.length === 0`, `...(flow.length === 0 && column.alignment !== "T" ? { startsHorizontalMode: true } : {})`, `(column.alignment === "T" && flow.length === 0) || flow.at(-1)?.kind === "columns" ? { leadingDisplayBaselineSkipPt: 0 }` (3567-3571).
- Then a post-hoc fixup that mutates `prepared.leadingSkipPt` three separate ways by `prepared.kind` (3576-3640): `leadingBlock || (previousDepth != null && (prepared.kind === "block" || paragraphNeedsInterline))`; a tcolorbox branch; a `\addvspace`-overlap branch that fishes a `trivlist-boundary` glue out of the laid paragraph and sets `leadingSkipPt - overlappingSkip + addedInterline`; and a separate columns-after-X branch `glue < 0 ? 1 : glue` (`1` is `\lineskip`, hard-coded as `1`, also as `TEX_LINE_SKIP_PT` in frame-flow.ts:10 and again in `interline + displayGlue < 0 ? 1 - displayGlue : interline`).
- `measureColumnVerticalBox` (4132+) and `emitPreparedColumns` recompute the minipage's height/depth/reference per alignment (T/t/c/b) with separate depth rules for "last item is block", "last is columns", "last is paragraph closing in glue" (`closesWithGlue`, `closesNestedList` using `lastList.role.depth > 1 && !noParList && !inheritsPendingLabel`).

Real mechanism: `beamerbaseframecomponents.sty:202-268`: `beamer@columnenv` is literally `\begin{minipage}[\beamer@colalign]{#2}\leavevmode\raggedright\beamer@colheadskip\ignorespaces`, with `\beamer@colheadskip` empty for c/t/b and `\vskip-1ex\nointerlineskip` for T. A column is therefore exactly LaTeX `minipage` content (a vlist built with normal `\parskip`/`\prevdepth` rules), and `\end{minipage}` does the `\unskip`/box packing. The same applies to frame body (`beamerbaseframe.sty` minipage / vbox) and to `rounded` block bodies (which `startsInMinipage: plan.style === "rounded"` hand-flags, 2446/2474).

Refactor direction: one `VListBuilder` (items: box with h/d, glue with natural/stretch/shrink and a `lastskip`/`prevdepth` state, penalty) that the three callers feed and that implements `\addvspace`, `\nointerlineskip`, `\lineskip` fallback, minipage packing (`[t]`, `[b]`, `[c]`, `\unskip` at end) once. Columns/blocks/frames become configuration (`minipage(align)`, `headskip`) over it. This is the same refactor as the (known) spacing work but it is the structural precondition; the beamer side should adopt the vlist/box model that `text/tex/vlist` already has rather than a parallel `leadingSkipPt`/`trailingSkipPt` scalar pair. Size: large (2-3k lines moved, mostly deletion), risk high; mitigated by the fuzzer.

### H2. Source-text regex/string inference of TeX structure in the paragraph prep path
Locations: render.ts:2084, 3623, 3780-3786, 3811, 3844-3847, 4403, 4565, 5495-5512; frame-flow.ts:282-310 (`trailingBeamerTrivlistSkip(source, ...)`, `trailingBeamerListSkip(source, ...)`, `leadingBeamerTrivlistAdjustment`).

Representative lines:
- `const startsWithTrivlist = /^\s*(?:(?:\\par(?![A-Za-z@])|\\(?:visible|uncover|invisible)\s*<[^>]*>\s*\{|\{)\s*)*\\begin\s*\{\s*(?:center|flushleft|flushright)\s*\}/u.test(paragraphSource)` (2084)
- `new RegExp(\`^\\s*\\\\${leadingSize.command}\\s*\\\\begin\\s*\\{thebibliography\\}\`)` (4403) to decide whether to treat a size command as ambient.
- `/\\(?:begin\s*\{\s*center\s*\}|centering)(?![A-Za-z@])/u.test(mapped.text) ? "font" : ... "font-fixed"` (4565): chooses the space-glue profile from whether the text mentions center anywhere.
- `trailingScopedBeamerListSkip` (5465-5533) scans `\end{itemize|enumerate|description}` matches, checks the gap between consecutive ends with `/^(?:\s|\}|\\par(?![A-Za-z@]))*$/`, tests whether the list began on an `\item` label line with `/\\item\s*(?:<[^>]*>\s*)?(?:\[[^\]]*\]\s*)?$/`, and then sums `topsep + enclosing parsep` per nesting depth. This is a textual re-simulation of what `\endlist`/`\@endparenv`/`\@topsepadd` leave in the vertical list.
- `const colorChange = syntax.controls.some(control => control.name === "color" && ...)` plus `environment.name` regex `^(?:center|flushleft|flushright|figure|table)$` (3615-3625) to emulate "`\color` in vertical mode places a color-stack operation between the previous skip and the trivlist, so `\addvspace` sees no skip".

Why it is wrong-model: these answer questions that the already-built vlist (`paragraph.layout.vlistLayout.boxReport.items`) can answer exactly (the last item is glue with origin X; is there a whatsit between). The code does both: it re-parses source with regex to predict, then also inspects `boxReport` items (e.g. `.find(item => item.glue?.origin?.kind === "trivlist-boundary")`) and reconciles with `Math.max`/`Math.min`. Hidden overlay branches, macros that expand to `\begin{center}`, and `\only<>{\begin{center}}` variants are only handled where someone wrote a regex branch for them (`\\(?:visible|uncover|invisible)\s*<...>\s*\{`).

Refactor direction: have `text/tex/vlist` report, per laid paragraph, a structured "start/end state" (first item kind, `lastskip` with origin, `prevdepth`, enclosing list depth/noparlist, pending whatsits) and make all trailing/leading logic read that. Delete the regex helpers. Size medium (~600 lines removed from render.ts/frame-flow.ts), risk medium, and it is mostly spacing-adjacent, but the regexes also drive non-spacing decisions (space-glue profile at 4565, bibliography size at 4403), which should become explicit paragraph properties from the parser instead.

### H3. Block/theme templates as a closed enum plus fitted constants, not evaluated templates
Locations: `theme/blocks.ts:20-80` (`style` derived by `templateId.includes("/inmargin") ? ... "rounded" ... "modern" : "default"`), render.ts `prepareBlockWithTheme` (2339-2736, 400 lines), 15+ `plan.style === "..."` branches in render.ts (2369, 2405, 2412, 2413, 2446, 2454, 2474, 2544, 2551, 2560, 2567, 2568, 2572, 2640, 2653, 2778, 2793, 3088, 3190), the title-page `rounded` constants (1976-1990: `4 * TEX_POINTS_PER_BP + 2.5`, `(plan.shadow ? 4 : 2) * TEX_POINTS_PER_BP + .5`), and `theme/resolve.ts` appliers (`applyModernInner`, `if (family === "metropolis")` 21 times in resolve.ts, 13 in templates.ts, 19 in render.ts).

Representative lines:
- `const terminalBodySkip = plan.style === "rounded" ? ... terminalBodyFlow.trailingListGlue.naturalPt + (terminalBodyFlow.trailingTrivlistSkipPt ?? 0) + (... > 0 ? 0 : terminalDisplaySkip(...)) : terminalBodyFlow?.kind === "block" ? ...afterSkipPt : 0 : 0;` (2544-2548)
- `const titleBodyGap = plan.style === "default" && geometry.flowBoxHeight === "title-ascent" ? (titleBodyInterline >= 0 ? titleBodyInterline : 1) : geometry.titleBodyGapPt;` (2653): `1` is `\lineskip` again, and `titleBodyInterline` is a hand-rolled `\baselineskip` computation.
- `closesWithBodySkip = plan.style === "default" && (trailingBodySkip > 0 || closingAlignmentSkip > 0 || terminalGlueKind === "external-flow-after" || ... )` with the explanatory comment "A default colorbox ending in vertical glue has zero physical depth" (2640-2648).

Real mechanism: `beamerbaseauxtemplates.sty:752` (`\defbeamertemplate{block begin}{rounded}`, `{block end}{rounded}` at 760), `beamerbaseboxes.sty` (`\beamerboxesdeclarecolorscheme`, `\beamer@setupbox`, `\beamerboxesrounded`), `beamerinnerthemedefault.sty` (block begin/end: `\par\vskip\medskipamount`, `\begin{beamercolorbox}...\usebeamerfont*{block title}...\vskip-.25ex`, then `\begin{beamercolorbox}` body, `\end{beamercolorbox}`). A block is a short macro sequence of `\par`, `\vskip`, colorbox (a vbox/minipage with `\fboxsep`-like padding), so all the "closes in glue means zero depth" cases fall out of the vlist model (H1) automatically: a colorbox is `\vbox{... \unskip}` style packing.

Refactor direction: model each template as a small declarative "box program" (list of `par`/`vskip`/`colorbox{title|body}`), keep the numeric constants as data in one table with the .sty line reference, and let the H1 vlist builder pack it. The `style` branches in render.ts disappear because the differences become different programs. Size medium-large, risk medium; the theme resolver can stay table-driven (it is data), but variant behaviour (metropolis/moloch/inmargin) should not leak into render.ts as `if` ladders.

### H4. Frame vertical packing is a pseudo-glue model (`fillWeight` scalars, `TOP_ALIGNED_FRAME_SKIP_PT`)
Locations: `resolveFrameVerticalPacking` (render.ts ~5280-5330), `renderBeamerFrameStep` 823-850, `item.contents.fillWeight`, `titlePage.leadingFillWeight/trailingFillWeight`, `fillUnit` passed through `positionPreparedFrameFlow(flow, baselineSkip, fillUnit, initialPreviousDepth)`.

What it does: for c/t/b alignment it computes a single `fillUnit = (freeHeight - topOffset)/(1 + internalFillWeight)` and adds `fillWeight * fillUnit` to a few item kinds (title page, contents) only. Comments cite `beamerbaseframe.sty` ("top-aligned frames get a natural .2cm top skip; their finite stretch is dominated by the bottom `1fill`"), `symmetric-frame-center` option, and `shrink ? "top" : alignment` overrides. User `\vfill`, `\vspace*{\fill}`, `\hfill` equivalents inside the frame body are not part of this (grep shows `fillWeight` handled for only two item kinds), and plain-frame `initialPreviousDepth` is `null` vs `0` as a boolean switch (`frame.options?.plain ? null : 0`, repeated twice at 831/845).

Real mechanism: `beamerbaseframe.sty` wraps the body in a `\vbox to \textheight` or `\vtop` with `\vss`/`\vfill`/`\vskip.2cm plus 1fill` glue depending on `\beamer@frametopskip`/`\beamer@framebottomskip`; the stretch is distributed by TeX's glue-setting over all stretch in the box, including user `\vfill`. Treating fill as a per-item weight is an approximation that works for the two item kinds tested.

Refactor direction: once H1 has real glue items (natural/stretch with order fil/fill/filll), frame packing becomes "set the vbox to height h" over that list, with the frame's top/bottom glue inserted per the .sty. Also lets `\vfill` in user text work. Size small-medium after H1; risk low-medium.

### H5. Inline-flow (blocks/columns nested inside lists/text) uses placeholder boxes plus a fixed-point iteration over mutable shared state
Locations: render.ts 1514-1568 (`prepareInlineFlow`), 1013, 1142, 1349, 4445, 4521-4540; `inline-flow.ts`.

What it does: nested `block`/`columns` get laid out by calling `prepareFrameFlow` recursively, stored in `references.inlineFlow` (mutable array replaced by index), projected into the text as `\begin{minipage}{1pt}X\end{minipage}` placeholders, and list item labels that "transfer" to the placeholder are tracked in `references.inlineFlowItemLabels` (a `Map` mutated during `layoutParagraph`, compared with `JSON.stringify(...) !== JSON.stringify(...)` at 4534) and `inlineFlowLabelState.revision`. `prepareInlineFlow` then loops `for attempt <= candidates.length` re-running `prepareFrameFlow` until the revision stops changing, and throws "Deferred Beamer item label transfer did not stabilize". `labelTargetOffset` is chosen as the first visible `itemize|enumerate|description|center|flushleft|flushright` environment inside the span.

Why it matters: the placeholder idea is the right one (a laid-out box dropped into a horizontal/vertical list) but the iteration over mutated references means layout results depend on the order and count of passes; this is a classic source of "works for the fuzz corpus case, breaks for a neighbour". Real LaTeX has no such iteration: a box in an item is simply the first object after `\item`'s label hbox.

Refactor direction: after H1/H2, layout of an `\item` whose first content is a block/columns should be a single pass: box into the item's vlist with `\parindent`-less label. Replace the revision loop with a pure function of (item, nested box). Size medium, risk medium.

### H6. `layoutParagraph` and `prepareFrameParagraph` are catch-all parameter funnels
Locations: render.ts:4364-4905 (541 lines), 2031-2115, 3507-3684.

Pattern: pass a ~25-field options object (`bounds`, `font`, `inMinipage`, `listProfile`, `initialPreviousDepth`, `leadingDisplayBaselineSkipPt`, `startsHorizontalMode`, `spaceGlueProfile`, `alignment`, `justify`, ...). Callers retry layout with a changed flag: `paragraph = layoutParagraph(layoutParams)` then, `if (paragraph && params.firstInColumn && startsWithDisplay && !closesInitialLine && params.leadingDisplayBaselineSkipPt !== 0) paragraph = layoutParagraph({ ...layoutParams, leadingDisplayBaselineSkipPt: 0 })` and `else if (paragraph && startsWithDisplay && initialPreviousDepth !== undefined) paragraph = layoutParagraph({ ...layoutParams, initialPreviousDepth })` (3815-3818). Laying the paragraph twice and picking the second result is a signal that the first-line/display-start state is not known before layout; the `\mbox{}` injection at 3780 ("A column starts with `\leavevmode`, so a leading `\par` ends a paragraph holding only an empty line") is a source-text rewrite to emulate `\leavevmode`.

Refactor direction: put `\leavevmode` / "in horizontal mode at start" in the layout context as a mode (vertical/horizontal) that the vlist code understands, instead of injecting `\mbox{}` and relayouting. Size small-medium, risk low-medium; best done with H1.

### H7. Overlay visibility handled at call sites (33 uses of `resolveBeamerOverlaySpanVisibility`/`hasProjectedContent` in render.ts)
Locations: e.g. render.ts 852-861 (`placement.item.visibility === "hidden" && !["block","paragraph","columns","tikzpicture"].includes(placement.item.kind)`), 2084-2090, 2490-2520, 3405+, `hasProjectedContent`, plus `overlay.ts` (`projectBeamerOverlayText` 745, `projectBeamerTikzSource` 1232).

Each flow builder re-checks `visibility === "removed"` / `"hidden"` and decides separately what "hidden" means per item kind (covered vs absent), and a list that exists only in a hidden branch is special-cased ("A structural list node spans its enclosing group, so a list that only appears in an overlay branch hidden at this step leaves plain text", 3783) with a regex on the projected text (`isVisibleList`). Real mechanism: `beamerbaseoverlay.sty` `\only`/`\uncover`/`\visible`/`\invisible`/`\alt` act on the typeset box (only = not typeset; uncover/invisible = typeset, then covered via `\beamer@cover`/color). Overlay.ts itself (parsing, tests, few commits) is fine; the leak is in render.ts.

Refactor direction: project overlay once per step into the IR (remove `only`-hidden nodes, mark covered ones) before flow preparation, so builders see only present nodes with a `covered` flag. Size medium, risk low-medium.

### H8. Magic constants and named-size lookup scattered in render.ts
`TOP_ALIGNED_FRAME_SKIP_PT = 0.2*cm` (202), `topsepPtByDepth` / `BEAMER_LIST_LAYOUT_PROFILE` with a fallback `?? 9`, `?? 3` (frame-flow.ts `topsepPt = 9`, `= 3`), `.5` `liveListTopsepPt` in frame-shrink.ts:60 (correct per comment, but a hard-coded duplicate of `\beamer@cramped`'s effect), `1` as `\lineskip`, `.75 * fontXHeightPt` in blocks.ts (`\beamer@colorsep`-derived), `0.25` in title page, `2.2 * xheight` in frame title padding. Most carry a comment citing a .sty but are not co-located with the source reference. Direction: one `beamer/constants.ts` keyed by `file: macro`, registered as data (see H3).

## 3. Cross-cutting observations

1. **No shared box/glue/vlist abstraction on the Beamer side.** `text/tex/vlist` has a real box/glue report (`boxReport.items`, glue `origin.kind` like `trivlist-boundary`, `display-math-interline`, `display-math-boundary`, `external-flow`), but Beamer composes with scalar fields (`leadingSkipPt`, `trailingSkipPt`, `closingEnvironmentSkipPt`, `trailingTrivlistSkipPt`, `trailingListGlue.{naturalPt,shrinkPt}`, `endingDepth`, `afterSkipPt`, `trailingVerticalSpacePreviousDepth`) on `PreparedFrameFlowItem`. Every new boundary case adds a field and a branch. There are at least 7 skip-like scalars on a prepared paragraph and block-level `plan.geometry.{beforeSkipPt, afterSkipPt, boxTopSkipPt, titleBodyGapPt, ...}`. Items 1, 3, 4 and 6 above all go away if the flow is a real vlist.
2. **Code mirrors the macro in places, but at the wrong level.** `frame-shrink.ts` is a model of how to do it: one function per macro, integer sp arithmetic, a comment citing `beamerbaseframesize.sty`. The block/column code instead pattern-matches on outcomes ("closes in glue so depth is zero"). Where a macro is cited in a comment (about 60 `.sty` references in render.ts), the citation usually explains a branch rather than a structure.
3. **Duplicated list/trivlist closing logic across layers.** `trailingBeamerListSkip`/`trailingBeamerTrivlistSkip` (frame-flow.ts), `trailingScopedBeamerListSkip` (render.ts:5465), `closesNestedList` (4163) and the vlist layer's own list closing in `text/tex/vlist` encode `\endlist`/`\@endparenv` separately. This is the known spacing problem; it touches this area at H1/H2.
4. **State carried by mutable shared `references` object** (`inlineFlow`, `inlineFlowItemLabels`, `inlineFlowLabelState`, `ambientTextAt`, `scopedTheme`, `frameLayout`). Layout is order dependent. Prefer immutable per-call context with results returned.
5. **File organisation as a symptom.** A 5.5k-line file with 54 top-level functions, several over 250 lines and a 600-line frame function, makes it hard to see that columns, blocks and frames are the same thing. Splitting by mechanism (flow, minipage, block-template, title-page, footnote-insertion) is cheap and should follow, not precede, H1.
6. **Leaf mechanisms are in good shape.** Shrink, overlay parsing, footnotes, captions, theorems, bibliography, continuations show 1-4 commits each and cite their macros; they do not need attention.

Suggested order: H1 (vlist builder, shared with the spacing effort) -> H2 (delete regex inference using vlist state) -> H3 (declarative block templates) -> H4/H7/H6 (follow-ons) -> H5.
